htaccess-manager.php

.htaccess management – the plugin's own block in Apache's .htaccess

Pure file operations: every function takes the file path (or the rule inputs) as a parameter and registers no hooks - except jpkcom_postfilter_htaccess_file() and jpkcom_postfilter_htaccess_available(), which find the site's file and read the server. Wiring them to admin actions, options and version changes is the job of the callers; nothing in this file writes on its own.

WHY NOT insert_with_markers()

WordPress's insert_with_markers() appends a new marker pair at the END of the file - after WordPress's own block, where a reject rule never takes effect (WordPress's RewriteRule . /index.php [L] has already sent every filter URL to PHP; measured, research report 4 §1.2). And removing through it with an empty list leaves the marker lines behind. So this file places, replaces and removes the block itself (spec 7):

  • The managed block sits directly before the line # BEGIN WordPress, or at the top (after a UTF-8 BOM) when there is no WordPress block. An existing managed block above WordPress's is replaced where it stands; one below it is moved directly before it (ruling R15).
  • A block with the MANUAL markers (# BEGIN JPKCom Post Filter (manual), the copy snippet) is never touched: write refuses, remove leaves it. Two blocks would apply the same rules twice. Markers are compared as whole lines, so the managed marker - a prefix of the manual one - never matches the manual line.
  • Writes happen under flock(LOCK_EX) on the file itself, in place (fopen 'r+', fwrite, ftruncate) - no temp file and rename, so owner, group and mode of the .htaccess survive. A shrinking write is padded with comment lines to the old length first, so Apache never reads a remnant of the old content. Nothing is written when the content would not change.
  • Line endings (LF or CRLF, taken from the file's first line break), a UTF-8 BOM and a missing trailing newline are kept; every byte outside the managed block stays as it was.

jpkcom_postfilter_htaccess_parse()

htaccess-manager.php : 113

Split .htaccess content into lines and find the markers

jpkcom_postfilter_htaccess_parse(string $content) : array{bom: string, eol: string, lines: string[], blocks: array, damaged: bool, manual: bool, wp: ?int, misplaced: bool}

Each line keeps its own terminator (\n, \r\n or none for a last line without newline), so joining them gives back the exact bytes. Markers are compared as whole lines, ignoring surrounding blanks.

damaged means managed markers that do not pair up (BEGIN without END, END without BEGIN, BEGIN inside a block), or a managed block that holds one of WordPress's own marker lines (it spans or overlaps WordPress's block): where the block ends is then a guess - or replacing it would take WordPress's rewrite rules with it - and write and remove refuse.

misplaced means the first managed block sits below # BEGIN WordPress, where it never takes effect.

Parameters
$content : string

jpkcom_postfilter_htaccess_put()

htaccess-manager.php : 426

Replace the content of an open, locked file

jpkcom_postfilter_htaccess_put(resource $fh, string $content) : bool

Writes from offset 0 first and cuts the rest afterwards, so the file is never empty in between. A shorter content goes out padded with comment lines to the current size in one write (jpkcom_postfilter_htaccess_padded()), so no reader ever sees a remnant of the old content before the cut.

Write, flush and cut are silenced: on a full disk fwrite() raises an E_NOTICE, and with display_errors on that would be output before the redirect of the Set up / Remove action ("headers already sent"). The failure is reported through the return value (T8-b).

jpkcom_postfilter_htaccess_rule_units()

htaccess-manager.php : 601

The lines of a managed block as comparable units

jpkcom_postfilter_htaccess_rule_units(array<string|int, string> $lines) : array<int, array{reject: bool, text: string}>

A reject rule - the three lines RewriteCond %{ENV:REDIRECT_STATUS} ^$, RewriteCond %{THE_REQUEST} "<pattern>", RewriteRule ^ - [E=JPKPF_REJECT:server-<reason>,R=<status>,L] (or ^/) that jpkcom_postfilter_server_apache_rules() writes per reason, in exactly that shape (1.7.1, M-3) - is one unit; every other line is a unit of its own. The rule hash is taken out: the # rule <hash> line is dropped and the hash of an X-Jpkpf-Rule header line blanked. It names the rule set; what is rejected does not depend on it. So is the text of a string ErrorDocument <status> "…" line (a complete quoted string, escapes allowed): it is the page's body in the locale of whoever wrote the block, and a body cannot reject anything. Directive and status stay; an ErrorDocument that is not one complete quoted string (a URL, an open quote) is compared as it is.

Parameters
$lines : array<string|int, string>

Lines between the markers, without line endings.

array<int, array{reject: bool, text: string}>

jpkcom_postfilter_htaccess_provably_looser()

htaccess-manager.php : 678

Is a new managed block provably no stricter than the one in the file?

jpkcom_postfilter_htaccess_provably_looser(string $content, string $block) : bool

"Provably looser" (R161-3) is decided on the text alone - no pattern is evaluated, so nothing depends on how a server reads a regular expression. True only when:

  • the content parses without damaged markers and holds a managed block;
  • $block is '' (no reject part any more): removing a block only ever loosens; or else
  • there is no manual block (write() refuses next to one), the managed block does not sit below WordPress's (it never took effect there, and writing would move it up into effect), and
  • the units of the new block (jpkcom_postfilter_htaccess_rule_units(), rule hash taken out) are exactly the units of the file's first managed block with zero or more whole reject rules deleted: same order, every other unit byte for byte the same - the patterns of the rules that stay, the reject status, the header lines, the ErrorDocument directive and status (its quoted text may differ: a translation), RewriteEngine and <IfModule> lines.

So the new block rejects a subset of what the old one rejects. Anything else - a rule added, a pattern changed (even to a looser one), another status, an ErrorDocument that is no longer a quoted text, a line edited by hand - is not provable, and the answer is false. Further managed blocks in the file are dropped by write(), which only loosens.

The reject rules of one block carry different reasons, so matching the units in order, earliest first, finds the deletion when there is one.

Parameters
$content : string

File content.

$block : string

New managed block (jpkcom_postfilter_htaccess_block()), '' for none.

Tags
since
1.7.1
Return values
bool

jpkcom_postfilter_htaccess_home_file()

htaccess-manager.php : 778

Path of the site's .htaccess as WordPress derives it: get_home_path()

jpkcom_postfilter_htaccess_home_file() : string

get_home_path() reads SCRIPT_FILENAME when home and siteurl differ (WordPress in a subdirectory). That is the PHP script of the request: the wp binary under WP-CLI, the root index.php on a front-end request - and from there the home path came out as '/' and the file as '/.htaccess'. So SCRIPT_FILENAME is ABSPATH for the call, which is what get_home_path() expects to find it below (WP-CLI's own rewrite command does the same); on an admin request the result is unchanged. When even that yields no home path (home and siteurl on different hosts), the WordPress directory is taken - never the file system root.

jpkcom_postfilter_htaccess_file()

htaccess-manager.php : 828

Path of the site's .htaccess

jpkcom_postfilter_htaccess_file() : string

The path stored at Set up (option jpkcom_postfilter_htaccess_managed, fix wave item 1) while that file exists - a WP-CLI command, a cron run or a deactivation then works on the file the admin set up, whatever the request looks like. Otherwise (not set up, the legacy value '1', or the site moved and the stored file is gone) jpkcom_postfilter_htaccess_home_file().

The stored path is only trusted when its directory is one of the site's own: the WordPress directory, its parent (WordPress in a subdirectory) or the derived home path. A tampered option must not point the writes at another .htaccess on the host, and a subdirectory such as wp-content/uploads is never the right file either.

jpkcom_postfilter_htaccess_available()

htaccess-manager.php : 943

May the plugin manage the .htaccess on this site?

jpkcom_postfilter_htaccess_available() : array{ok: bool, reason: string}

Reasons, in the order they are checked:

  • litespeed: LiteSpeed reports itself as such, and WordPress's $is_apache is true for it too; OpenLiteSpeed also needs a restart to read .htaccess changes, so the plugin does not manage it there.
  • not-apache: SERVER_SOFTWARE does not name Apache (nginx, Caddy, FrankenPHP, Ferron, IIS, none).
  • multisite: one .htaccess serves the whole network.
  • file-mods-disallowed: DISALLOW_FILE_MODS is set.
  • no-file, not-writable, not-readable: jpkcom_postfilter_htaccess_file().
  • manual-block: a pasted block with the manual markers is present; a second, managed one would apply the same rules twice.

The first four come from jpkcom_postfilter_htaccess_site_reason(), the rest from jpkcom_postfilter_htaccess_file_reason(). The capability and nonce checks belong to the admin action.
