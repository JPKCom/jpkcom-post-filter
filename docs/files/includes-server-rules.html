server-rules.php

Server Rules – what a web server may reject before PHP runs

No hooks are registered here: the inputs are read from WordPress on demand, everything else is pure, so tests/test-server-rules.php can fuzz the patterns against the real request guard without a server. The snippets built from these patterns live in includes/server-rules-render.php.

WHY THIS EXISTS

The 1.5.0 request guard answers over-cap filter URLs with 410, but only after the WordPress bootstrap - on the production site that prompted 1.5.0 the bootstrap alone was enough to exhaust PHP-FPM. A web server can turn the same URLs away for almost nothing, provided its rule is never stricter than the plugin: a server rule must never match a URL the plugin answers with 200 or 301. Looser is fine; PHP still has the last word.

The patterns read the RAW request URI (nginx $request_uri, Apache THE_REQUEST, Caddy {http.request.uri}, Ferron request.uri) and only ever match a path without %. WordPress tries every rewrite rule on the raw path and then on its urldecode()d form (WP::parse_request()), so an encoded %70age, jpkpf%2Dfragment or %2F splits the filter path differently from its raw bytes; leaving every % path to PHP rules that out entirely.

They use only what PCRE (nginx, Apache, OpenLiteSpeed), RE2 (Caddy) and Rust's regex (Ferron) share: literals, negated classes, non-capturing groups, * + ? {n} {n,} {n,m}, alternation and anchors. No lookaround, no backreferences - one grammar, one fuzz test for every server.

jpkcom_postfilter_server_rule_inputs()

server-rules.php : 140

The effective values a server rule is generated from

jpkcom_postfilter_server_rule_inputs() : array{strict: bool, max_per_group: int, groups: int, skip_positions: int[], reject_status: int, endpoint: string, fragment: string, bases: string[], verdict_filtered: bool, policy_filtered: string[], hash: string}

Effective means after constants, stored settings, defaults and the jpkcom_postfilter_{key} filters - what this request's guard would use. A filter that answers differently per request cannot be seen from here, which is why policy_filtered and verdict_filtered are reported.

Bases: every routable post type that gets rewrite rules, in every language jpkcom_postfilter_archive_base_urls_all_languages() knows, as paths including the home path. A missing base only makes the rule looser. For a base the plugin derives itself (post type archive, posts page, WPML language directory) a path it does not route is one WordPress would 404 anyway. That is NOT proven for bases a callback on jpkcom_postfilter_robots_txt_base_urls adds (multilingual plugins other than WPML): the filter feeds the server rejects too, so if other code serves {base}{endpoint}/a+b+c/ below such a base, the server would reject it. A callback must return only bases the plugin routes.

jpkcom_postfilter_server_reject_patterns()

server-rules.php : 298

The two patterns a server may reject a filter URL on

jpkcom_postfilter_server_reject_patterns(array<string, mixed> $inputs[, string $subject = 'uri' ]) : array{per_group: ?string, segments: ?string}

Regexes without delimiters, for the raw request URI (path plus optional query). With B = the bases without their leading /, E = endpoint, N = terms per group, G = filter groups:

per_group: a segment below {B}{E}/ with N+1 or more non-empty pieces separated by literal + segments: segment G+1 contains a +, or there are G+4 segments

Why that is never stricter than the plugin, for a path without %:

  • urldecode() changes nothing but + there, and no rewrite rule literal contains +, so WordPress captures from the raw path.
  • The capture is the path after {E}/ minus an optional page/N / fragment suffix - at most three segments, none with a +. A segment with a + is therefore always part of the capture, and of G+4 segments at least G+1 are.
  • The guard rejects more than G non-empty segments (segments), and since 1.6.0 more than N non-empty raw pieces per taxonomy, counted before sanitize_title() and de-duplication (per-group). A literal + always separates pieces; %2b joining does not apply without %. Pieces of one taxonomy add up across segments, so one segment over the cap is enough.
  • A position whose group has no taxonomy is not counted by the guard, so per_group then only looks at the other positions - or at a position past G, which is a segments reject anyway.
  • per_group looks for the over-cap segment up to position G+3 only (bounded repetition, no JIT stack per segment); past that, and without %, segments matches anyway - with %, nothing does.

Both null when strict URLs are off, the guard's verdict is filtered (code may decide per request), there are no groups, no bases or no endpoint, or one base lies below another base's endpoint (a URL could then be captured by either base's rules, positions shifted). per_group is also null when N is 0 (unlimited).

request_line builds the same grammar for Apache's and OpenLiteSpeed's %{THE_REQUEST}, "METHOD URI PROTOCOL": anchored ^[A-Z]+ ... (?:\s|$), every negated class also excludes whitespace and the query is (?:\?\S*)?. The whitespace matters - "HTTP/1.1" contains a /, so a class that may cross the space counts "jpkpf-fragment HTTP/" as one more segment, and /blog/filter/a/b/page/2/jpkpf-fragment would be rejected although the plugin serves it. A URI cannot contain whitespace in a request line, so on every real request both forms decide the same. This form is PCRE-only (\s, \S); only the URI form is for RE2/Rust.
