server-rules-check.php

Server Rules status check, and the notice after a loosening save

Spec 8. Two things, both about server rules the admin pasted into a web server configuration - the plugin cannot see or change those:

  • "Check now" (jpkcom_postfilter_server_check_run(), called by the Server Rules page; no background job): loopback requests to the site's own URLs. robots.txt must carry the plugin's lines; a synthetic over-cap URL shows by its X-Jpkpf-Reject / X-Jpkpf-Rule headers whether the server or PHP rejected it and from which settings the server rule was built; a URL with exactly N terms - one the plugin serves - must never be rejected by the server. The rate limit is not probed: that would use up the request budget all cookie-less visitors share. A loopback the site does not let through (HTTP authentication, firewall, maintenance mode, timeout) is "unreachable" with its reason - never "missing".
  • The notice: after every save of the General or Filter Groups page that loosens the rule inputs (spec 7: N higher or 0, a group or a position without taxonomy added, strict URLs off, another endpoint or base) the saving admin is told to update deployed server rules - whether or not a check ever ran, red when the last check found them active or stale. Nothing is blocked. Not when the plugin manages the .htaccess block itself: includes/htaccess-sync.php keeps that one in step.

The probes, classification and the "looser" comparison are pure functions on top of includes/server-rules.php and includes/server-rules-render.php (the probe URLs are the ones the printed curl commands use); the hooks for the notice are at the end of this file.

WHY THE "BEFORE" STATE IS CAPTURED ON sanitize_option_* (PRIORITY 4)

The plugin's settings sanitizer (priority 10) writes the settings cache file, and the plugin reads that file before the database - from then on the effective inputs are the new ones. So the inputs before the save can only be read before priority 10. A first save goes update_option() -> add_option() and sanitizes twice; the second run would read the new state, so the first capture of a save is kept until the commit hook takes it.

jpkcom_postfilter_server_probe_urls()

server-rules-check.php : 74

The URLs the status check requests

jpkcom_postfilter_server_probe_urls(array<string, mixed> $inputs) : array{robots: string, over: ?string, at_cap: ?string}

Origin of home_url() plus the paths of jpkcom_postfilter_server_probe_paths() for the snippet inputs - the same URLs the printed curl commands probe. over: N+1 probe slugs at the first position with a taxonomy (/blog/filter/jpkpf-probe-1+…+N+1/); with N = 0 (unlimited) there is no per-group rule, and the segments probe (G+4 segments) takes its place. at_cap: a URL the plugin serves that is closest to the rule - N probe slugs, or G segments for N = 0. Both null when the settings produce no reject pattern. robots.txt is always at the host root, where crawlers read it.

Parameters
$inputs : array<string, mixed>

As returned by jpkcom_postfilter_server_rule_inputs().

jpkcom_postfilter_server_check_classify()

server-rules-check.php : 248

Turn the probe answers into a status

jpkcom_postfilter_server_check_classify(array<string, mixed> $responses, array<string, mixed> $inputs, string $server_software[, bool $robots_expected = true ]) : array{robots: string, rule: string, stricter: bool, stricter_checked: bool, stricter_suspected: bool, detail: string}

robots: ok when the body carries the plugin's fragment line (/*jpkpf-fragment), disabled when the plugin writes no robots.txt lines on this site, not-wordpress when something else answers robots.txt (a physical file, the web server), unreachable when the request did not get through.

rule (the over probe): active for X-Jpkpf-Reject: server-… with X-Jpkpf-Rule equal to the current hash, stale with another or no hash, missing when PHP's own reject header (no server-) answered, unknown for an answer without the header - OpenLiteSpeed cannot send one with its reject, and a proxy may remove it - unreachable for a transport error, 401, 403, 429, 5xx or a redirect, none when the settings produce no reject pattern.

stricter (the at_cap probe, a URL the plugin serves): true only on proof - the server rejected it with server-…. That is the red alarm. stricter_suspected: on LiteSpeed a 404/410 without header (OpenLiteSpeed rejects without one, but so does WordPress for a base it does not route), a hedged warning, never the alarm (ruling R19). stricter_checked: false when the at-cap probe did not get through (timeout, 401, 429 - the loopback sends no cookies, so a rate limit catches it -, 5xx, ...) or there was nothing to check; the detail then says why.

$inputs : array<string, mixed>

Rule inputs the probes were built from.

$server_software : string

SERVER_SOFTWARE of this site.

$robots_expected : bool = true

Does the plugin add lines to robots.txt on this site?

jpkcom_postfilter_server_rules_is_looser()

server-rules-check.php : 395

Does going from $old to $new loosen the rule inputs?

jpkcom_postfilter_server_rules_is_looser(array<string, mixed> $old, array<string, mixed> $new) : bool

True when union( $old, $new ) differs from $old (spec 7: N higher or 0, a group or a position without taxonomy added, strict URLs off, another endpoint, fragment or base, a filtered verdict). Compared on the values that shape the rule, as sets where they are sets; the hash is ignored. A state without groups rejects nothing whatever strict says, so strict counts only with groups. The reject status is left out (ruling R20): 404 or 410 changes how a rejected URL is answered, not which URLs are rejected.

Parameters
$old : array<string, mixed>

Inputs before the change.

$new : array<string, mixed>

Inputs after it.

jpkcom_postfilter_server_check_run()

server-rules-check.php : 472

"Check now": probe the site, classify, store

jpkcom_postfilter_server_check_run() : array{time: int, result: array{robots: string, rule: string, stricter: bool, stricter_checked: bool, stricter_suspected: bool, detail: string}}

GET robots.txt, HEAD on the over-cap and the at-cap URL (both skipped when there is no reject pattern). Only URLs built from home_url(); timeout 5, redirection 0, no cookies, and TLS verification as core's own loopbacks (Site Health) decide it: https_local_ssl_verify, default false - a loopback often reaches a local certificate the system does not trust, and the probe carries no secrets. The result goes to the option jpkcom_postfilter_server_rules_check (not autoloaded) as {time, result}. The caller checks capability and nonce.

sanitize_option_{option}, priority 4: remember the inputs before the save

jpkcom_postfilter_server_check_capture_before(mixed $value[, string $option = '' ]) : mixed

Before the settings sanitizer (10) rewrites the cache file.
