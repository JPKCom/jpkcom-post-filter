url-policy.php

URL Policy – which filter URLs exist, and in which form

No hooks are registered here, so the rules can be exercised without WordPress (tests/test-url-policy.php) and reused by every caller that has to agree on them - the URL builder, the parser, the request guard, the link helpers and the Abilities API.

WHY THIS EXISTS

Until 1.5.0 the plugin accepted every spelling of a filter selection and rendered it with HTTP 200: b+a, a+b and a+a+b were three self-canonical pages, a fourth term over the cap was silently dropped, and every term link in the filter bar pointed at "current selection + this term" in click order. A handful of terms therefore spanned millions of distinct URLs, each one a full WordPress render, and crawlers that follow links never ran out of new ones. Measured on a production site: ~840 000 filter requests a day, every URL unique, the PHP-FPM pool exhausted.

The fix is to make the URL space finite and canonical: one spelling per selection (slugs sorted and de-duplicated), hard caps that reject instead of truncate, and one source of truth for both.

Since 1.6.0 the per-group cap counts the non-empty raw pieces of a group (after splitting, before sanitize_title and de-duplication), so a web server rule can mirror it exactly by counting +-separated pieces in the path.

jpkcom_postfilter_normalize_filters()

url-policy.php : 210

Bring a filter map into its one canonical form

jpkcom_postfilter_normalize_filters(array<string|int, mixed> $filters) : array<string, array<string|int, string>>

Slugs are sanitised, de-duplicated and sorted byte-wise ascending within each taxonomy; empty taxonomies are dropped. Byte order needs no database and is what JavaScript's default Array#sort produces for slugs (ASCII and lower-case percent escapes), so the browser builds the same URL.

Before 1.5.0 the order was the click order, so a selection of k terms had k! spellings, each of them a self-canonical page and a separate cache entry.

$filters : array<string|int, mixed>

jpkcom_postfilter_known_term_slugs()

url-policy.php : 387

All term slugs of a taxonomy, in every language

jpkcom_postfilter_known_term_slugs(string $taxonomy) : array<string|int, string>|null

Deliberately not jpkcom_postfilter_get_terms_for_taxonomy(): that list goes through get_terms(), which WPML (and similar plugins) narrow to the current language, and its transient is keyed by taxonomy only - so the language that happened to warm the cache decided which slugs existed. Since 1.5.0 an unknown slug is redirected away, which would have silently dropped every term of the other languages from their URLs.

One query per taxonomy per cache lifetime; the transient is keyed by taxonomy, never by requested slugs, and flushed with the term caches.

The one authority on "does this slug exist" - the request guard, the robots decision and the Abilities API all ask it, so "unknown" means the same thing everywhere. (No hooks, which is why it lives here.)

Parameters
$taxonomy : string

Taxonomy key.

jpkcom_postfilter_split_segment()

url-policy.php : 480

Split a path segment into its term slugs

jpkcom_postfilter_split_segment(string $segment[, callable|null $known_slugs = null ][, string $taxonomy = '' ]) : array<string|int, string>

%2B counts as the separator too. Some link rewriters and normalisers encode +, and WordPress passes the escape through to the query var unchanged; read as part of one slug it made the whole selection "unknown" and redirected it to the unfiltered archive.

Except where %2b is part of a real slug. WordPress does not create such slugs itself (sanitize_title( 'C++' ) is c), but one typed into the slug field or imported as c%2b%2b is kept verbatim. A part that is a known slug stays whole; an unknown one is split at %2b and adjacent pieces are joined back, longest first, wherever they form a known slug - so c%2b%2b%2Bzaeune (two slugs joined by an encoded +) reads as c%2b%2b and zaeune.

jpkcom_postfilter_validate_filter_path()

url-policy.php : 565

Classify a requested filter path

jpkcom_postfilter_validate_filter_path(string $path, array<string|int, string> $taxonomies[, callable|null $known_slugs = null ][, string $unknown_action = 'redirect' ]) : array{action: string, reason: string, filters: array, unknown: bool}

Decides between "reject" (the path can never be a valid selection on this site) and "ok" with the normalised selection it stands for. Whether an ok path has to be redirected is decided by the caller, by comparing the request against the URL built from filters - one comparison that covers order, duplicates, case, empty segments, page/1 and the trailing slash.

Order of checks:

  1. more segments than filter groups -> reject (segments)
  2. a slug longer than 200 characters -> reject (length)
  3. caps per group, group count, total terms -> reject (per-group, groups, total) (per-group counts the non-empty raw pieces, summed per taxonomy, before normalising; see the file header)
  4. unknown slugs, per $unknown_action: redirect: dropped (the caller then redirects to what is left) noindex: kept, flagged reject: reject (unknown)

Before 1.5.0 the parser silently ignored extra segments and truncated over-cap selections, and every such URL rendered with 200.

Parameters
$path : string

Filter path as captured by the rewrite rule.

$taxonomies : array<string|int, string>

Taxonomies in position order.

$known_slugs : callable|null = null

fn( string $taxonomy ): ?string[] - known slugs, null when the taxonomy is gone. Null callable = no existence check.

$unknown_action : string = 'redirect'

'redirect' | 'noindex' | 'reject'.
