htaccess-sync.php

.htaccess sync – keeps the managed block in step with the settings

The managed block (includes/htaccess-manager.php) may never be stricter than the plugin, not even for one request: a server that rejects a URL the plugin would answer with 200 or 301 breaks the site. So the block follows every change of the inputs it is built from (spec 7):

  • A save of the General or Filter Groups page first brings the block to the UNION of the current and the submitted state - looser than either - and only then lets WordPress commit the option. After the commit the block is brought to the new state, which tightens it where the save tightened.
  • When the block cannot be loosened (file not writable, markers damaged, .htaccess management no longer available) the save is refused: an error for the admin, and option, settings cache file and .htaccess all stay as they were.
  • One save at a time (1.7.1, T9-d): a lock is held from the loosen step to the tighten step. A second save of General, Filter Groups or an import that starts meanwhile is refused - loosening from values the first save has not committed yet could leave the block stricter than what that save commits.
  • Options outside the plugin that move the archive bases (page_for_posts, permalink_structure) sync after the commit; constants and filters change the effective values without any option event, so admin_init compares the hash in the file with the current one.

WHY sanitize_option_* ON PRIORITY 5

update_option() runs sanitize_option() first, and the plugin's settings sanitizer (priority 10) writes the settings cache file as a side effect - the plugin reads that file before the database, so from that moment on it runs with the new values. pre_update_option_* comes too late. Priority 5 loosens the block before the cache file is written.

Refusing works through the same filter: it hands on the stored value instead of the submitted one, and a last filter on PHP_INT_MAX hands on exactly the value update_option() compares against (get_option()) and puts the cache file back on the stored value - the sanitizer at 10 has just rewritten it from that value, which is not necessarily byte-identical to what is stored (a partially stored array gains keys). update_option() then sees no change and returns false without a hook (wp-includes/option.php 7.1.3:923-925). A first save goes update_option() -> add_option(), which sanitizes a second time (:1113); a refused first save never gets there.

jpkcom_postfilter_htaccess_loosen()

htaccess-sync.php : 588

Make sure the .htaccess is no stricter than the given inputs

jpkcom_postfilter_htaccess_loosen(array<string, mixed> $inputs[, bool $orphan = false ][, array<string, mixed>|null $current = null ]) : array{ok: bool, reason: string}

Writing a looser block, like removing one, is always safe, so it is attempted whenever the file holds a managed block and is writable - whatever jpkcom_postfilter_htaccess_available() says and whatever SERVER_SOFTWARE names (empty under WP-CLI). Where the plugin may manage the file, a missing block is written, too.

True when the block was brought to the inputs, already is as strict as them, the file holds no managed block that could be stricter, or the server positively does not read .htaccess (nothing more is done; the block stays for the Remove action and deactivation). False, with a reason, when a managed block (or markers that no longer pair up) stays stricter on a server that may read it (ruling R22).

An orphaned block (managed markers in the file, option gone - e.g. a deactivation that could not remove it) is not brought to the inputs but removed: nothing would keep it in step afterwards.

A write that failed half way and could not be undone (jpkcom_postfilter_htaccess_last_error() rollback-failed) is reported as write-unrestored ahead of every other reason: the file may be incomplete, and the admin has to check it, not just retry (T8-a).

A file that exists but cannot be read (T9-e) holds a block nobody can see, possibly stricter than anything: not-readable, like damaged markers - unless $current is given and the inputs reject exactly what it rejects (the save loosens nothing, so whatever the block is, it is not made stricter than the plugin by this save).

$inputs : array<string, mixed>

Rule inputs (usually a union).

$orphan : bool = false

The block is in the file without the managed option.

$current : array<string, mixed>|null = null

Inputs the plugin runs with before the save (1.7.1).

jpkcom_postfilter_htaccess_save_lock()

htaccess-sync.php : 814

Take the save lock, held from the loosen step to the tighten step (T9-d)

jpkcom_postfilter_htaccess_save_lock() : string

Two saves at once break "never stricter": B loosens from the values A has not committed yet and can write a block stricter than what A then commits. So one save at a time - for a managed block only; a site without one sends no query.

The option jpkcom_postfilter_htaccess_save_lock holds "|", inserted with INSERT IGNORE like core's WP_Upgrader::create_lock(): the row either goes in or it is there already, nothing in between. The request holding it may take it again (add_option() sanitizes a second time, an import saves two options). Released after the tighten (jpkcom_postfilter_htaccess_after_save()), on a refusal, after an import, and at the latest by a shutdown function

  • which PHP runs after a fatal error, too. A lock older than a minute belongs to a request that died without even that (killed); it is taken over, atomically, so two takers cannot both win.

Without $wpdb (never the case in WordPress) there is nothing to lock with, and the save goes on.

A statement that fails ($wpdb->last_error, a false result) is not another request's lock: INSERT IGNORE turns a duplicate key into a warning, so an error means the options table could not be used. That is db-error (M-6) - before, it ended as busy, and the admin was told to wait for a save that did not exist.

jpkcom_postfilter_htaccess_before_delete()

htaccess-sync.php : 1356

delete_option (core, before the row goes): loosen for the defaults (I-2)

jpkcom_postfilter_htaccess_before_delete(string $option) : void

Deleting jpkcom_postfilter_general or jpkcom_postfilter_filter_groups deletes the group's settings cache file too (T2-b), and from then on the plugin runs with what it falls back to - the defaults, or no groups at all. That can be looser than the block (stored N1, default N2), so the block is first brought to union( current, state after the delete ), under the save lock, like a save.

When the block cannot be loosened (or another request holds the save lock, or the lock statement fails), the delete is refused before core deletes the row: the lock is released, then WP_CLI::error() ends wp option delete with exit code 1, and anywhere else wp_die() answers 409 with the reason. Option, cache file and .htaccess stay as they were, like a refused save (user decision, 1.7.1 re-review). Keeping the cache file instead (1.7.1-dev) left the stricter values in a store the plugin treats as disposable: with the settings file cache switched off it is never read, and "Clear Settings File Cache" deletes it - either way the plugin fell back to the defaults while the block stayed strict.

core's delete_option() offers no filter to stop it; this action runs before its DELETE, so ending the request here is the only way.

$option : string

Option name.

jpkcom_postfilter_htaccess_maybe_resync()

htaccess-sync.php : 1458

admin_init: sync when the file's hash is not the current one

jpkcom_postfilter_htaccess_maybe_resync() : void

Constants and filters change effective values without an option event. A block below WordPress's (it never takes effect) is moved, too. Only on admin page loads - not on admin-ajax (heartbeat), REST or cron requests (ruling R18), and only for a user who can manage_options (not for an anonymous request to admin-post.php). Known limit: a constant that loosens between two requests leaves the block stricter until the next admin page load. No write while another request is between its loosen and its tighten (T9-d): this request may still read the values before that save, and the save's own tighten writes the current state anyway.

Cheapest first, since this runs on every admin page (1.7.1): the site checks before the managed flag (not autoloaded, so a query - T9-b), the file read once, and on an equal hash nothing is rendered (T9-a). The hash still runs the size guard once (jpkcom_postfilter_server_patterns_dropped(), R161-4); rendering the block would run it twice more. Returning on an equal hash is safe because a # rule line is only written with a non-empty block, and the same hash means the same rule - as long as a renderer change bumps jpkcom_postfilter_server_renderer_version().

jpkcom_postfilter_htaccess_lifecycle()

htaccess-sync.php : 1535

Activation and version change

jpkcom_postfilter_htaccess_lifecycle() : void

Managed: sync (a new version may build other rules from the same settings). Not managed but a managed block is in the file - the plugin was deleted without being deactivated and installed again, say: remove it, it must never stay with outdated limits. Removing only ever loosens, so it does not wait for jpkcom_postfilter_htaccess_available(); a manual block is never touched. Nothing is set up.

Managed, but SERVER_SOFTWARE is empty (WP-CLI, a system cron) or names an unknown server that may read .htaccess (R161-3): the block is rewritten only when the new one is provably looser (jpkcom_postfilter_htaccess_provably_looser(): it drops whole reject rules and adds none). A 1.6.0 block with a rule the size guard now drops makes Apache answer 500 for the whole site, so PHP only ever runs under WP-CLI there - and on a server the plugin cannot see, it never tightens. Everything else stays as it was until the next admin page load on Apache.

Under WP-CLI SERVER_SOFTWARE is empty, so available() answers not-apache before it looks at multisite, DISALLOW_FILE_MODS, LiteSpeed or a manual block: the repair runs on such a site as well (M-2). It is loosen-only, like a loosening save under DISALLOW_FILE_MODS (F-4). Next to a manual block it can only remove the managed block (the new one is '', no reject part any more); deleting a rule there is not provable. On a web request those reasons stop the version change here - no sync, no repair - and so does a server that positively ignores .htaccess.
