server-rules-render.php

Server Rules – rendering: rate limits, reject body and per-server snippets

Pure: everything here works on the inputs and patterns of includes/server-rules.php and returns text, so tests/test-server-rules.php can check every snippet without a server. No hooks are registered.

Every snippet follows the same scheme (spec 5.3): a reject answers with the configured status, X-Robots-Tag: noindex, nofollow, X-Jpkpf-Reject: server-<reason>, X-Jpkpf-Rule: <hash> and Cache-Control: no-store; a rate limit only applies to filter URLs of requests without any Cookie header, and its 429 carries no X-Robots-Tag.

The bases a snippet may contain

jpkcom_postfilter_server_safe_bases(array<int, mixed> $bases) : array<string|int, string>

A base ends up in nginx strings and location prefixes, Apache quoted arguments, shell commands and HTML. WordPress paths are normally plain slugs, but nothing forbids a quote, space, brace, $, ; or newline in a custom rewrite slug or home path - and browsers percent-encode most of those, so a raw-path rule would not match them anyway. Such a base is left out of the snippets (looser, never stricter). Allowed: RFC 3986 unreserved characters plus ! * + , = : @.

The rate-limit numbers of every server snippet, from one formula

jpkcom_postfilter_rate_limits(int $workers, float $render_seconds) : array{conn: int, rate: int, burst: int, ip_per_minute: int, ip_burst: int, bot_rate: int, bot_burst: int, retry_after: int}

Inputs are what an admin knows: W = PHP workers (1-256), t = render time of a filter page in seconds (0.05-10).

conn = max(1, floor(3W/8)) at most 3/8 of the workers render cookie-less filter pages at once, the rest stay free for the site rate = max(1, round(0.4 conn/t)) requests/s site-wide: keeps those workers 40 % busy on average burst = 2 rate ip_per_minute = 30, ip_burst = 10 a visitor without cookie gets 11 quick clicks, then one every 2 s bot_rate = max(1, round(2 rate/3)), bot_burst = 20 search engines' own bucket retry_after = 10 s

Anchor (spec 6, research report 3 §3, production: 8 workers, 0.4 s): conn 3, 3 r/s burst 6, 30 r/min burst 10 per IP, search engines 2 r/s burst 20.

jpkcom_postfilter_server_snippets_apache()

server-rules-render.php : 885

Apache snippets: VirtualHost reject, mod_qos cap, ModSecurity limits

jpkcom_postfilter_server_snippets_apache(array<string, mixed> $inputs, array<string, int> $limits) : array<int, array{id: string, title: string, context: string, code: string}>

mod_qos (research report 4 §3a): QS_EventRequestLimit is a real concurrency cap on cookie-less filter requests. Never QS_ClientEventLimitCount: measured, it bans the client IP for every URL, cookie users included.

mod_qos has no bucket of its own for search engines: exempting their User-Agent would let anyone who fakes one past the only concurrency cap, so they share it (spec 6).

ModSecurity (§3b): everything inside a <LocationMatch> over the filter prefixes (decoded path - fine for a rate limit), including SecRuleEngine On, so OWASP CRS is not switched to blocking for the rest of the site. Phase 2, because Apache maps a request to its Location only after phase 1 rules ran (post_read_request). Fixed-window counters. The window starts with the first request (expirevar only when the counter is created); research set expirevar on every hit, which re-arms it - steady traffic then never resets a site-wide counter, and a visitor clicking every few seconds is blocked for good. Every deny rule is chained to its own class (cookie- less visitor or search engine), so a counter another rule set keeps cannot trigger it.

The counters live in RESOURCE (key jpkpf_ip_<addr>) and USER (key jpkpf_site_<server name>, via setuid), not in IP and GLOBAL: OWASP CRS 3.3 opens ip as <addr>_<UA hash> and global as global in phase 1, and ModSecurity 2 ignores a later initcol of an open collection. Measured on Debian 13 (CRS 3.3.7, modsecurity.conf active): a new User-Agent per request walked past the per-IP limit, and one VirtualHost's site-wide counter answered 429 on another. Custom collection names are not addressable in ModSecurity 2 ("Unknown variable").

jpkcom_postfilter_server_snippets_caddy()

server-rules-render.php : 1142

Caddy snippet: one `route` with the rejects first, then `rate_limit`

jpkcom_postfilter_server_snippets_caddy(array<string, mixed> $inputs, array<string, int> $limits) : array<int, array{id: string, title: string, context: string, code: string}>

Research report 2 §2. path_regexp sees the decoded path, so the reject is a CEL expression on the raw path and query. Both the reject and the rate-limit scope read the ORIGINAL request ({http.request.orig_uri}, {http.request.orig_uri.path}): the Caddyfile sorts rewrite and try_files before route, so a site-level try_files would otherwise have rewritten {http.request.uri} and path to /index.php first and silently disabled both. The original path is not cleaned, which is why the scope allows leading slashes (scope_regex()).

The pattern sits in a double-quoted CEL string inside a Caddyfile backtick token: the backticks pass every byte through, CEL then reads \\ as one backslash - so each \ of the pattern is doubled (\\+). A root base renders as an empty alternative (?:|news/), which RE2 accepts.

route keeps the written order. Outside it caddy-ratelimit sorts itself before respond, and every rejected request then used up the budget of the cookie-less visitors (verified in research). Inside it the segments block comes first: its respond ends the route, so a URL over both caps gets the guard's reason. The reject carries no-store - a cached reject would outlive a later loosening (spec 5.3).

Rate limit (caddy-ratelimit, sliding window of events per window): per IP ip_burst in the time ip_per_minute needs for them, site-wide (key static) and search engines' own zone over 10 s. Any Cookie header exempts. The 429 page carries no-store but no X-Robots-Tag: a busy answer for a valid URL must not tell search engines to drop it.

jpkcom_postfilter_server_snippets_ferron3()

server-rules-render.php : 1272

Ferron 3 snippets: top-level `match` blocks and host-level `if` blocks

jpkcom_postfilter_server_snippets_ferron3(array<string, mixed> $inputs, array<string, int> $limits) : array<int, array{id: string, title: string, context: string, code: string}>

Research report 2 §3.1 (3.0.0-rc.10, .conf format). match goes at the top level, where every host can use it (rc.10 also takes it inside a host), if only inside a host, hence two blocks. The reject matches request.uri (raw; request.uri.path is decoded) in a raw string r"…", so the pattern goes in unchanged; a root base's empty alternative (?:|news/) is valid in Rust's regex since 1.8. The if is decided once on the original URI, before any rewrite stage. The per-group matcher excludes the segments pattern, so a URL over both caps gets one status and the guard's reason.

Rate limit: rate_limit is a token bucket with an integer rate per second (1 is the smallest), per IP. Ferron has no constant key, so there is neither a site-wide rate nor a bucket of their own for search engines. Instead a FastCGI bulkhead: a second fcgi_php with its own connection pool, keyed by the URL string - it must differ from the main URL - and limit connections; further requests wait. The plugin does not know the backend URL: <php-backend-url> is a placeholder. A Unix socket cannot take the /jpkpf suffix (Ferron connects to the URL's whole path, so every request failed with 500 in the lab); a second spelling of the same path (/./) is the separate pool there.
