crawl-guard.php

Crawl Guard – keep the filter URL space finite for bots and caches

Everything a crawler sees of the filter, in one place:

  • the request guard: 301 to the one canonical spelling, 404/410 for paths that can never be a valid selection - decided on the request filter, before the main query runs;
  • the internal query vars, which are only ever taken from the rewrite rule;
  • robots directives (meta tag for core, Rank Math and Yoast, plus an X-Robots-Tag header) and exactly one canonical;
  • robots.txt rules for the combination space;
  • the term links of the filter bar, which decide what a link-following crawler can discover in the first place.

WHY THIS EXISTS

See includes/url-policy.php. In short: every term link pointed at "current selection + this term" in click order, nothing was ever rejected, and every spelling rendered as a separate indexable page. A link-following crawler found millions of URLs from a few dozen terms, and a page cache keyed on the URL never hit. Bots are not locked out by any of this: content, the archive and the single-term filter pages stay crawlable and indexable. What goes away is the maze.

jpkcom_postfilter_restrict_internal_query_vars(array<string, mixed> $query_vars) : array<string, mixed>

jpkcom_postfilter_canonical_decision()

crawl-guard.php : 458

Where the canonical of the current filter page points

jpkcom_postfilter_canonical_decision() : array{kind: string, url: string}|null

Reads the canonical settings and the term count, never the robots directives - those are derived from this decision.

  • bot page (unknown term, no results): none
  • page 2 and later (since 1.7.1): self with the page, as Google asks for paginated pages - within seo_index_max_terms, else none; the duplicate of the archive is page 1. off stays none.
  • one term, canonical_single: archive (the term archive when it is an indexable target, else as filter) / filter / off
  • two or more terms, canonical_multi: home (the archive base when it is an indexable target, else as filter) / filter / off
  • filter: self when the page is within seo_index_max_terms, else none
  • off: none

The URL then passes jpkcom_postfilter_canonical; an empty value makes the decision none (since 1.7.1), so the term-count noindex stays.

array{kind: string, url: string}|null —

jpkcom_postfilter_robots_directives()

crawl-guard.php : 537

Robots directives for the current filter page

jpkcom_postfilter_robots_directives() : array{index: bool, follow: bool}|null

One decision for the meta tag (core, Rank Math, Yoast) and the HTTP header. A filter page is noindex, nofollow when it combines more terms than seo_index_max_terms (default 1), names an unknown slug, or has no results on page 1. Single-term pages stay index, follow.

Since 1.7.0 a canonical to another URL (the term archive or the archive base, see jpkcom_postfilter_canonical_decision()) replaces the noindex that comes from the term count: noindex next to a canonical pointing elsewhere is a contradiction search engines resolve unpredictably, at worst by carrying the noindex over to the target. follow keeps following the term count. Bot pages are not affected.

nofollow is deliberate: everything such a page links to is reachable from the archive, the single-term pages and the sitemap. Following its links only leads further into the combinations.

jpkcom_postfilter_robots_txt_rules()

crawl-guard.php : 968

robots.txt rules for the filter URLs

jpkcom_postfilter_robots_txt_rules() : array<string|int, string>

Applies to every user agent alike - no crawler is locked out of content or of the single-term pages, only out of the combinations.

  • deep (default), with seo_index_max_terms = 1: {base}/{endpoint}/*+ any segment with more than one term Not *\/*\/ (proposed in the original analysis): it would also block _/term/ - the single-term pages of the second group, which the default link mode links to and which are indexable - and the pagination of every single-term page. Blocked but linked pages end up "indexed, though blocked by robots.txt". Two-segment combinations are not linked in single mode and are noindex anyway.
  • all: the whole endpoint
  • off: nothing

With seo_index_max_terms = 0 "deep" becomes "all"; with 2 or more the indexable pages cannot be told apart by a wildcard, so only the fragment and query-var lines are emitted.

jpkcom_postfilter_term_href()

crawl-guard.php : 1072

Where a term button links to - or null for no link at all

jpkcom_postfilter_term_href(string $base_url, array<string, array<string|int, string>> $active_filters, string $taxonomy, string $slug, bool $is_active) : string|null

The script never reads these hrefs: it intercepts every click and builds the URL from the button states. The hrefs serve clients without JavaScript, which in practice means crawlers. They are therefore the generator of the URL space a crawler can discover, and the link mode decides its size:

  • single (default): an inactive term links to its own single-term page, an active term to the selection without it while at most one term is left. Crawlable: the archive plus one page per term.
  • combo: "current selection ± this term", as before 1.5.0, but never beyond the caps, never deeper than JPKCOM_POSTFILTER_LINK_MAX_TERMS, and on an empty result page not into another group (that can only narrow nothing further).
  • none: no hrefs, buttons only.
